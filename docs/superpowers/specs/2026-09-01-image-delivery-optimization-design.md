# 博客图片交付优化设计

日期：2026-09-01

## 1. 目标

解决三个已经确认的问题：强制刷新时加载页咖啡图出现得晚，首页为小卡片下载原始封面，正文继续使用体积偏大的 PNG、JPEG 和 GIF。

处理完成后，当前 Jekyll 站和后续 Astro 站共用同一批优化图片。图床 `master` 只保留仍在使用的原格式文件和生成后的 WebP；转换成功且博客不再引用的原图从 `master` 删除。原件继续保存在远端备份分支。

## 2. 当前基线

- 博客源码有 280 处图床引用，对应 278 条不同路径。
- 图床清理后的 `master` 有 278 张图片，约 88.28 MiB，另有 1 个 PDF。
- 删除前快照保存在 `backup/pre-image-cleanup-20260901`。
- 首页卡片直接使用 `image.path`，没有单独的缩略图字段。
- 加载页咖啡图为 500×500 的透明 PNG，大小 217874 字节；页面没有预加载声明。

以上数字是设计时基线。实现脚本不得依赖固定数量，必须从博客引用和图床 tree 重新计算。

## 3. 文件和引用约定

图床新增两个目录：

```text
img/optimized/<原文件名>.<原扩展名>.webp
img/thumbnails/<原文件名>.<原扩展名>.webp
```

把原扩展名保留在新文件名中，可以区分同名的 PNG、JPEG 或其他来源文件。路径逐段做 URL 编码，博客文件中保存可直接访问的 jsDelivr URL。

转换脚本生成 manifest，记录原路径、优化后路径、缩略图路径、源大小、源格式、源宽高、页数、输出大小、输出宽高、是否采用输出、跳过原因和引用位置。动画的高度按单帧记录，不使用 Sharp 返回的堆叠总高度。manifest 用于更新链接、验证和回滚，不靠文件名猜测迁移关系。

## 4. 转换规则

### 4.1 正文和完整封面

- PNG、JPEG、无扩展名 JPEG 和 BMP 输出为 WebP，质量 88。
- 宽度超过 1920px 时按比例缩到 1920px；较小图片不放大。
- 保留透明通道和 EXIF 方向，删除与显示无关的元数据。
- 只有输出文件比原文件小才采用；否则保留原格式和原 URL。
- SVG、现有 WebP 和 AVIF 默认不转换。
- GIF 尝试输出动态 WebP。采用前必须确认帧数、循环次数和各帧延迟一致，并且输出更小；任一条件不满足就保留 GIF。

技术截图和文字图使用偏保守的质量参数。管线不按照片与截图分别猜测质量，也不对正文图片做裁剪。

### 4.2 首页缩略图

- 每篇已发布文章都生成独立缩略图，不只处理当前第一页。
- 尺寸为 640×336，比例 40:21，居中裁剪，WebP 质量 82。
- GIF 封面只取第一帧生成静态缩略图；SVG 可栅格化为缩略图，但完整封面仍保留 SVG。
- 文章 front matter 在 `image.path` 之外增加 `image.thumbnail`。
- 首页模板优先使用 `image.thumbnail`，缺失时回退到 `image.path`。
- 文章页、社交预览和图片灯箱继续使用 `image.path` 对应的完整图片。

## 5. 加载页咖啡图

- 从现有 500×500 透明 PNG 生成同尺寸 WebP，质量 82。
- PNG 留作 `<picture>` 回退，不内嵌 base64。
- 在 `<head>` 添加 `rel="preload"`、`as="image"` 和 `type="image/webp"`。
- 实际图片使用 `loading="eager"`、`fetchpriority="high"` 和明确的宽高。
- 当前隐藏的蛋糕图降为懒加载和低优先级，避免与咖啡图抢同源带宽。
- 咖啡 WebP 必须小于 70 KiB；未达到时调整编码参数，但不缩小到低于 500×500。

## 6. 可重复运行的维护工具

博客仓库新增 Node 脚本，使用 `sharp` 处理图片。脚本接收图床本地路径，不把 GitHub 凭据写进代码，也不在普通 Jekyll 构建中自动修改另一个仓库。

命令分成三个阶段：

1. `audit`：只读扫描博客和图床，输出来源大小、转换资格、引用位置和输出计划。它不编码临时图片，因此不预测压缩后的字节数。
2. `apply`：生成优化图和缩略图，并更新博客引用；不删除原图。
3. `prune`：重新扫描引用，默认只写包含精确路径、字节数和状态绑定的删除计划；显式传入确认参数后，只执行与该计划完全一致的删除。

默认命令只执行 `audit`。`apply` 和 `prune` 必须显式指定。`audit` 和 `apply` 读取现有 manifest，把当前引用与历史 source/full/thumbnail 映射逐项核对。历史源 URL 被重新引用时，只修复链接；发布封面缺少缩略图或缩略图错误时，复用已有缩略图。只有新增原图需要编码。现有输出校验通过后，重复执行 `apply` 不改文件或 manifest。实际源图与输出图字节数在 `apply` 后写入 manifest，用于计算实际节省量。

工具使用 Node 内置测试框架验证 URL 解析、命名、尺寸决策、引用替换、GIF 跳过和删除保护。测试使用小型 fixture，不下载真实图床。

## 7. 两个仓库的提交顺序

迁移不能把“博客已引用但图床还没有”的 URL 发布到线上，也不能先删旧图。

1. 确认博客和图床工作树，记录图床 `master` 提交。
2. 从图床当前 `master` 建立 `backup/pre-image-optimization-20260901`。
3. 在图床生成优化图和缩略图，提交并推送新增文件，不删除原图。
4. 逐个请求新 URL，确认状态码、内容类型、尺寸和文件大小。
5. 更新博客 front matter、正文引用、首页模板和咖啡加载图，完成本地构建与浏览器检查。
6. 未经用户确认不推送博客 `master`，避免直接触发 GitHub Pages 部署。
7. 博客部署并核对线上页面后，再执行 `prune`，删除图床 `master` 中已迁移的原图。

如果实施阶段必须在同一会话完成，仍要保持上述提交边界。任何一步失败，都停在旧链接继续可用的状态。

## 8. 验证

自动检查：

- 先运行失败测试，证明当前没有缩略图字段、咖啡预加载和优化映射。
- manifest 中每个采用的输出都存在；完整图大小小于源文件，缩略图为 640×336。
- 所有博客图床 URL 在新 tree 中存在，没有 404。
- `prune` dry-run 报告绑定博客 HEAD、图床 HEAD、manifest SHA-256、发布提交、排序候选及总字节数，并计算计划 digest。确认模式要求原报告仍为 `planned`，重新计算全部绑定；任一差异都不会覆盖报告或删除文件。绑定一致后，命令再次验证 manifest 和 adopted outputs，再按计划删除。
- Jekyll 构建和现有测试通过；生成的首页使用缩略图，文章页使用完整图。
- 咖啡 WebP 小于 70 KiB，生成 HTML 含 preload 和高优先级属性。

浏览器检查：

- 使用空缓存访问首页，确认咖啡图请求从 `<head>` 发起且优先级为 High。
- 记录首页实际图片传输量，与优化前 11.6 MiB 基线比较。
- 检查桌面与移动端首页裁剪、正文文字图清晰度、透明背景、GIF 动画、SVG 和灯箱。
- 强制刷新与普通刷新各测一次，不用热缓存结果代替冷启动结果。

Node 管线测试不能证明 Jekyll 渲染和浏览器行为正确。Jekyll、htmlproofer 和空缓存浏览器检查是发布门禁；本地环境无法运行时，必须在功能分支 CI 和浏览器验证中补齐，不能据此宣称可部署或可删除原图。

## 9. 回滚

- 博客引用更新作为独立提交；回滚该提交即可恢复旧 URL。
- 图床优化文件作为独立提交；删除原图另做提交，不与生成操作混在一起。
- `backup/pre-image-optimization-20260901` 保存优化前的当前 tree；更早的 `backup/pre-image-cleanup-20260901` 保存清理前原件。
- jsDelivr 的分支缓存可能继续提供旧内容，验证以 GitHub tree、固定 commit URL和无缓存请求为准。

## 10. 不在本次范围内

- 不更换 GitHub Pages 或 jsDelivr。
- 不接入对象存储、Cloudflare Images 或付费图片服务。
- 不重写文章正文和图片说明。
- 不清理 Git 历史。
- 不推送博客、部署网站或修改 Pages 设置，除非用户在实现完成后明确确认。
