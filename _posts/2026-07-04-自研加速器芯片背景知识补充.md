## host-device 异构计算执行模型

Heterogeneous Computing（异构计算）指 CPU、GPU、NPU、FPGA 等不同处理单元协同工作。host-device 模型是其中最常见的一种，现代 GPU 以及各类自研 AI 芯片基本都是典型的 host-device 异构计算。CPU 作为 host 侧，负责组织、调度、加载、提交和同步；GPU 或 AI 芯片作为 device 侧，负责高吞吐张量计算；runtime、driver 和 firmware 把两边接起来。

执行模型本质上是解决软件如何驱动硬件计算的一套抽象，涵盖程序如何变成目标设备上实际运行的指令的全过程，是 ISA + ABI + OS 调度模型的集合。所谓可编程的功能，也需要通过具体的执行模型来实现。一段高级语言编写的代码要运行在异构计算设备中，执行模型大致如下：

```
模型代码: PyTorch / vLLM / TensorFlow / JAX / ONNX Runtime
-> 框架把模型拆成 OP / graph
-> 后端选择每个 OP 的执行设备: CPU、CUDA GPU、TPU、NPU 或自研 AI 芯片
-> dispatcher 或编译器决定每个 OP 怎么执行
-> runtime 分配显存、管理 stream/event、提交 kernel
-> driver 负责命令队列、DMA、中断和权限，把命令发送到设备
-> firmware / command processor 调度设备侧任务
-> 矩阵单元、向量单元、DMA、SRAM、HBM/DRAM 完成实际计算
结果回到框架 tensor
```

从微观上看，运行一个 host 程序的过程大致如下：

```
-> host程序启动
-> 初始化runtime
-> runtime调用driver打开设备
-> 创建context/stream/queque
-> 加载目标平台binary
-> 分配host/device内存
-> 拷贝数据到device可访问内存
-> 配置kernel参数
-> 提交kernel launch命令
-> driver写入命令队列
-> 目标硬件调度并执行binary中的指令
-> 执行完成后driver/runtime同步
-> 拷贝结果回host
-> 释放资源
```

## 仿真和验证

整个芯片不同的抽象层级大致可以分为：系统应用 Application--> 软件 Software--> 操作系统 OS--> 固件 Firmware--> ESL Model（SystemC / C++ / HLS）--> RTL（Verilog / VHDL / SystemVerilog）--> Gate Level（门级网表）--> Layout（版图）。

加速器芯片研发过程中一大工作量，就是在各种仿真环境中进行验证，完成代码在自研芯片上的功能测试和性能测试。仿真环境分为纯 CPU 进行逻辑上的仿真，以及进行 RTL 电路级别的仿真两种。

逻辑仿真中一大重要的方法学是 ESL（Electronic System Level，电子系统级）设计方法学，是 RTL 之上的一个抽象层级。ESL Model 是一种高抽象度的功能模型，用于在芯片设计的早期验证系统架构，而不描述具体电路。比如 Xilinx 的 HLS 就是 ESL 设计方法中的一种实现方式。ESL Model 具体又分 Function Model、Arch Model 和 Performance Model。Function Model 抽象层级最高，只关心输出是否正确；Arch Model 关注抽象的硬件结构，用于做架构探索；Performance Model 关注架构的性能

RTL 仿真分 Simulator 和 Emulator 两种，两种仿真环境都可以进行波形抓取来进行细粒度的问题定位和性能分析，区别在于前者是用软件解释或编译 RTL 来执行，后者是将 RTL 映射到专用硬件中执行。Simulator 的主流运行平台包括 Synopsys VCS、Cadence Xcelium 和 Siemens Questa；Emulator 的主流运行平台包括 Cadence Palladium、Synopsys ZeBu 和上海合见的 UVHS。Simulator 更灵活更方便，可以查看任意多的波形；Emulator 更快，比 Simulator 快出几个数量级，但价格也比 Simulator 贵出几个数量级。另外 Emulator 本质上也是在 FPGA 上运行，但相较于做 Prototype 的通用 FPGA，调试能力更强，更适合做大规模 SoC 的系统级验证工作。

## 性能分析和调试工具

Profiler 和调试工具也是一大工作量。没有 timeline、kernel trace、hardware counter、内存带宽统计、算力利用率、stall reason、graph dump、IR dump 和数值 diff 工具，芯片很难被客户稳定使用。一次慢运行必须能还原到具体 OP、kernel、layout、DMA、同步点或硬件模块。

算术强度（arithmetic intensity）指的是每搬运一字节数据所做的计算量，FLOP/Byte。

## 框架、算子和 kernel

框架接入是用户可见的入口，通过写 `torch.tensor(..., device="my_accel")`、`model.to("my_accel")`，或通过推理引擎，可以在目标设备上运行模型。Dispatcher 是框架内部的分派机制，用来根据 OP、dtype、device、layout 等信息选择具体后端实现。

OP（operator，算子）是框架语义层的“操作”。用户写的模型会被框架表示成一组操作，例如 matmul、softmax、reshape、attention。graph 是这些 OP 以及数据依赖关系组成的计算图。

kernel 是设备上真正执行的一段程序，由程序员声明并给定具体 shape、dtype、layout、tile 切分和并行策略等参数，在设备上由多个线程并行执行。在不同的目标设备上，kernel 的线程模型、内存层次和指令集可能完全不同。一个 OP 不一定对应一个 kernel。编译器可能把多个 OP 融合成一个 kernel（融合算子），一个 OP 也可能拆成多个 kernel。

OP 和 kernel 中间隔着图优化、layout 选择、tiling、memory planning、kernel selection、autotune 和 runtime 调度等，很多性能问题就藏在这个中间层：尽管语义上只是一个简单 OP，但落到设备上可能产生额外 layout conversion、低利用率 tile、同步等待或 HBM 往返等等。

典型算子可以粗略分几类：

| 类型       | 常见 OP                                         | 主要压力                               |
| ---------- | ----------------------------------------------- | -------------------------------------- |
| 矩阵计算   | matmul、GEMM、BMM                               | 矩阵单元吞吐、tile 利用率、HBM 带宽    |
| 逐元素计算 | add、mul、activation、quant、dequant            | 向量单元吞吐、访存开销                 |
| 归一化     | softmax、RMSNorm、LayerNorm                     | reduce、特殊函数、数值稳定性、片上缓存 |
| 形状和布局 | reshape、view、transpose、contiguous            | layout 表达、是否产生真实拷贝          |
| 注意力     | attention、RoPE、KV cache 访问                  | 矩阵计算、softmax、片上存储、显存带宽  |
| 稀疏/路由  | embedding、MoE、expert parallel                 | 随机访存、通信、负载均衡               |
| 通信       | allreduce、allgather、reduce-scatter、send/recv | 多卡互联带宽、拓扑、同步               |

## 编译器相关

编译器完成源代码到目标平台二进制文件的转化，是最难的工作之一。编译器前端要接 PyTorch、JAX、TensorFlow 或 ONNX 等框架，中端可能使用 StableHLO、MLIR、XLA 或自研 IR，后端再做 fusion（算子融合）、constant folding、shape specialization、layout optimization、memory planning、tiling、lowering、寄存器分配、指令调度、代码生成和 autotune 等。

编译器会基于底层硬件指令（ISA 操作语义）封装一系列 builtin 函数。程序员编写源代码并调用 builtin 函数来驱动硬件完成计算。Builtin 是编译器或语言内置函数，通常对应特殊硬件操作或低层能力。

ISA（Instruction Set Architecture，指令集架构）定义处理器能听懂哪些指令，规定了有哪些指令，有多少寄存器，每条指令的格式，地址空间，原子操作，内存模型等等，可能围绕矩阵乘、向量计算、load/store、DMA、同步、低精度转换等进行设计。对 AI 芯片来说，ISA 不一定像通用 CPU 那样暴露给普通程序员。它可能更多服务于编译器、手写 kernel 工程师和算子库。

## 可编程相关

Runtime 是高层运行时库，如 CUDA Runtime API，面向程序员提供了内存分配 malloc、设备之间的内存拷贝 memcpy、kernel 启动、module load、stream 任务队列、event marker 等功能，面向硬件通过调用 Driver 提供的接口实现对硬件的操作。现实路线通常是先做 CUDA-like 的窄 API，保证能分配内存、拷贝数据、加载 ELF、launch kernel 和同步，然后再补 stream、event、graph capture、异步执行和内存池等功能。

Driver 是直接管理硬件的软件，功能包括设备初始化、内存映射、命令队列提交、DMA、中断、上下文切换、binary 装载等。通过 Driver 的接口把指令给到硬件的 control 部分，硬件根据指令中各个位置的信息解码出 ISA 语义上的各个参数（shape、地址、模式等），并 trigger 硬件执行。

Memory Model（内存模型）是针对编程语言的概念，说明了有哪些 memory，并定义不同内存空间、cache、shared memory、SRAM、HBM 和主机内存之间的访问规则、生命周期、同步规则、搬运规则。内存模型描述了编程语言如何抽象和访问内存；存储器硬件只提供线性的地址空间，不同编程语言需要在这个线性空间上建立自己的软件抽象以便于程序员使用。C 抽象为字节序列+指针、Java 抽象为对象+堆、Python 抽象为对象+垃圾回收堆。内存模型的设计初衷是屏蔽硬件差异，保证程序在不同平台之间的可移植性。

## SiPU ESL Modeling 总体方案

`SiPU ESL Modeling总体方案` 这份文档把 SIPU Model 的目标定在三件事：架构硬件的功能/性能验证、软件开发验证调优、架构设计探索。核心思路是基于一套完整的软件栈，把 framework、测试/库、compiler、driver/runtime、firmware、CModel、QEMU、emulator 和 chip 串起来，让同一套 workload 可以落到软件模型、RTL/EMU 或真实芯片。

SIPU 驱动（Kernel Mode Driver, KMD）、运行时（User Mode Driver API, UMD / Runtime API）。

![SiPU 软件栈与仿真验证路径](https://cdn.jsdelivr.net/gh/HatrixXXX/Hatrix-s-Blog-Image/img/sipu-stack-clean.png)

这张软件栈图描述的是统一的运行和验证架构，不是单纯的 ESL Model 仿真流程，也不是单纯的真实芯片运行流程。上层可以来自 PyTorch、Triton 等框架，也可以来自 Arch Tests、Micro Arch Tests 或算子库测试。Host 侧和 Device 侧代码经编译器生成 executable，随后通过 runtime/driver API 下发到不同后端。

软件栈各层的职责可以这样理解：

- Framework 层包含 PyTorch、Triton 等框架入口，以及 Model Layer、DL Model 级别的测试。
- Arch Tests/Library 层包含 Arch/Micro Arch 级别的功能和性能测试，也包含算子库这类更接近真实场景的测试。
- Compiler 负责编译 Host 侧和 Device 侧代码，生成 executable 或 fatbin。
- Driver/runtime 向上提供 driver API 和 runtime API，向下连接用户态驱动、内核态驱动、仿真驱动和真实硬件。
- CModel 对 Driver、QEMU、Trace Player 提供统一的 model interface，Arch Model 和 ESL Model 都挂在这个接口后面。
- Emulator 和 Chip 是更靠近真实硬件的后端，前者用于硬件仿真或 emulation，后者对应真实芯片。

根据后端不同，同一套执行链路会分成几条路径：

- ESL Model 路径主要用于系统级仿真和早期验证。上层生成 executable 后，通过 driver API 进入 `sipu umd`，再走 `kmd emu interface` 到 `sipu kmd emu`，最后通过 `CModel Interface` 驱动 ESL Model。这条路径不依赖真实芯片，适合验证指令流、任务调度、内存访问、运行时和驱动行为。
- Arch Model 路径和 ESL Model 类似，也通过 `sipu kmd emu` 进入 `CModel Interface`，但后端落到 Arch Model。它更关注编程接口、ISA 语义、算子行为和架构状态变化，通常作为细粒度模型的 golden reference。
- Trace 路径用于问题复现和离线调试。系统运行时可以通过 Trace Dumper 把 driver/runtime 下发的命令、数据和寄存器配置记录成 Trace，再由 Trace Player 回放到 `CModel Interface`，驱动 Arch Model 或 ESL Model。文档里也注明 Trace Dumper/Player 当时还没有实现。
- Emulator 路径用于比纯软件模型更接近硬件的验证。`sipu kmd` 可以把任务下发到 Emulator，中间可能配合 QEMU 模拟 CPU/SoC 环境。这条路径更接近 RTL 或 FPGA/emulation 平台，运行成本也更高。
- 真实芯片路径是最终运行路径。上层框架或库生成 executable 后，通过 `sipu runtime` 或 driver API 进入 `sipu umd`，再通过 `ioctl` 调用 `sipu kmd`，最后由内核驱动控制真实 Chip 执行任务。

### 建模方案

文档把仿真模型分成三类：Arch Model、Function Model 和 Performance Model。当前 Function Model 与 Performance Model 是二合一实现，合在一起就是 ESL Model。

Arch Model 主要模拟 SIPU 的编程接口和 ISA 计算执行，需要保证计算逻辑、数值精度和硬件一致，但会尽量省略硬件模块内部细节。它开发周期短，调试方便，适合做架构级功能验证和细粒度模型的 golden reference。

![Arch Model](https://cdn.jsdelivr.net/gh/HatrixXXX/Hatrix-s-Blog-Image/img/arch-model-clean.png)

Arch Model 图里，`model interface` 是上层驱动入口。左侧 GCS 负责全局控制和 BD，下方连接全局/共享 Memory；右侧 SipuCore 里包含 Spike 和 TileCore 两类执行模型，Spike 侧有 `plic`，TileCore 侧有 `tcsr`。这张图强调的是编程接口和 ISA 执行路径，而不是完整硬件微结构。

这里几个缩写需要结合其他文档理解：

- `GCS` 是 Global Control System，全局控制系统。它接收上层提交的 kernel/packet，处理 pipe 或 ring buffer，解析 launch packet，把 kernel workload 打包并 dispatch 到后面的 cluster、PE 或 RV。
- `BD` 在现有文档里没有可靠全称，不能硬展开。能确定的是它接收 CCS 拆出来的 thread，配置 `tcsr`，给 RV 发送 kernel start interrupt，并在线程结束后把 Thread done signal 返回给 CCS。
- `Spike` 是 RISC-V ISA simulator。Arch Model 基于开源 Spike 执行 RV thread，并通过 tilecore extension 接入自定义 TileCore 指令，所以这里的 Spike 是 RV 指令执行模型，不是一个真实硬件模块。
- `plic` 是 RISC-V 的 Platform-Level Interrupt Controller，平台级中断控制器。在这张图里，它用于模拟 RV core 接收外部中断的路径，和 BD 触发 kernel start interrupt 的机制对应。
- `tcsr` 是 Tile Control and Status Register，TileCore 的控制/状态寄存器。BD 会在 thread 启动前配置它，Tile 相关指令也会通过 `TCSRR`、`TCSRW`、`TCSRWI` 读写它。

ESL Model 更接近硬件模块级结构。它包含 GCS、多个 PEC、DNoC XBar、DNoC Ring 和 C2C 互联。每个 PEC 内部又包含 PE、RV、Tilecore、L2C、L2B、ICI 和 Dram 等模块。

![ESL Model](https://cdn.jsdelivr.net/gh/HatrixXXX/Hatrix-s-Blog-Image/img/esl-model-clean.png)

ESL Model 图里的互联模块大致可以这样看：

- `ICI` 的全称在这批文档里没有展开。能确定的是，它位于 PE/MIF 和外部存储互联之间：PE 访问本 PE 内部 L2B 走 `PE-xBar`，访问外部存储单元则经过 MIF 上到 ICI 总线。地址转换在请求上传到 ICI 前完成，所以 ICI 和后面的 NoC 看到的已经是物理地址信息。
- `DNoC XBar` 是每个 PEC 下面的数据侧 NoC 局部交叉开关。`DNoC` 文档里没有直接展开，结合 `CNOC/DNOC` 命名和验证范围，这里按 data-side Network-on-Chip 理解；`XBar` 则负责把本地 PE、ICI、DRAM 等端口汇聚到更外层的数据 NoC。
- `DNoC Ring` 是更高一级的数据侧环形 NoC，把多个 PEC、DRAM 侧通路和 C2C 端口连接起来。这里的 Ring 是硬件互联拓扑，不是软件 ring buffer。
- `C2C` 可以确定是 chip-to-chip，用于跨芯片数据搬移。Memory 文档里说 C2C 模块需要处理 Host packet 或程序指令流产生的跨 Chip 搬移动作，并维护自己的 Cluster ID 和 DRAM 地址映射配置。
- `C2C Up` 和 `C2C Out` 的精确定义文档没有展开。结合图的位置，`C2C Up` 更像从本 chip 的 DNoC Ring 接到上级或外部 chip fabric 的 C2C 端口，`C2C Out` 更像外发方向的跨芯片出口；这部分属于合理推断，不能当作已确认的官方全称。

从抽象层级看，ESL Model 比 Arch Model 细。Function 仿真关注 HW module uarch、bit-accurate module interface 和 approximate timing，目标是做硬件验证的 golden reference，也给底层软件开发提供一个硬件模拟层。Performance 仿真关注和性能相关的硬件模块级时序行为，性能无关或影响较小的细节可以抽象掉，用来加快仿真速度。

PE 是 ESL Model 里最核心的执行单元之一。文档中的 PE 图把 dispatch、BD、RV Subsystem、Tilecore、Tsync、PE_xbar & L2B、MIF 等模块之间的控制和数据通路画了出来。

![PE 内部结构](https://cdn.jsdelivr.net/gh/HatrixXXX/Hatrix-s-Blog-Image/img/pe-model-clean.png)

PE 内部大致可以拆成几条通路：dispatch 进入 BD，BD 通过中断等方式驱动 RV Subsystem；RV Subsystem 里包含 RV、ACE 和 L2C；Tilecore 通过 `acp x2`、`asp x2` 与 RV Subsystem 交互，同时通过 `tlsu`、`tdte` 等接口连接 MIF；下方的 `PE_xbar & L2B` 负责 PE 内部互联和本地缓冲，MIF 则连向外部 memory fabric。`Tsync` 和 `tcsr r/w x2` 这类路径主要服务同步和控制寄存器访问。

PE 图里的几个接口和模块可以再拆细一点：

- `Tsync` 对应 Tile Sync。Arch Model 文档里写得比较直接：TSYNC 负责多个 thread 之间的同步，代码入口是 `tcore_exec_sync`。在实际 kernel 语义里，`tsync_*` 更偏 TileCore 指令同步，不自动等价于 CUDA `__syncthreads()`；涉及 RV/Tile 互访、DTE 写 L2B 后再读、Tile store 后 RV 读这类场景，还要配合 wait、ACE sync 或 cache 操作。
- `ACE` 是 Andes Core 的自定义扩展指令/接口路径。本地文档没有单独展开 ACE 缩写，但多处写作 Andes ACE；TileCore 指令基于 ACE instruction encoding，PE 编程建议也写明 TileCore 指令都是 Andes Core 的 ACE 扩展指令。它可以理解为 RV core 发射 Tile/自定义指令到 TileCore 的入口。
- `hvm x2` 在现有文档里只作为接口名出现，没有可靠全称。结合 `andesysc & ace interface` 里的 `hvm x2 & mem`，以及 `pe_xbar & L2B` 里的 `hvmx2`，这里可以把它理解成 RV/Andes 子系统到 `PE_xbar & L2B` 的两路高带宽/向量访存端口。
- `mem` 和 `hvm x2` 并列出现，能确定它是 RV/Andes 子系统侧的普通 memory 访问接口。图上它更偏通向 MIF/外部 memory fabric 的访存路径；具体协议、位宽和是否走 cache，文档没有展开。
- `tlsu` 是 Tile LSU，即 TileCore 的 load/store 模块，支持 load、store 和 atomic。Arch Model 文档里对应代码入口是 `tcore_exec_mem`，它会从 `memuop` 里解码访存格式和类型，执行普通 load/store、block load/store 和 atomic。
- `tdte` 是 Tile DTE，用来做大块数据搬运。Arch Model 文档里对应代码入口是 `tcore_exec_memacp`，支持 linear copy、tiled copy 和 tiled-linear-conversion；在算子实现里，它更接近 bulk/tensor data movement，不是标量 load/store。
- `MIF` 可以按 Memory Interface 理解。Memory 文档没有直接给全称，但明确说 PE 访问外部存储单元会经过 MIF 上到 ICI，总的地址转换功能块 ATU 放在 MIF 中，在请求上传到 ICI 之前完成地址转换。
- `PE_xbar` 是 PE 内部 crossbar/local bus，主要服务本 PE 内部 L2B/shared memory 访问。Memory 文档区分得很清楚：访问本 PE 内部 L2B 走 `PE-xBar`，访问外部存储单元才走 MIF 到 ICI。它和前面的 `DNoC XBar` 不是同一层级，`PE_xbar` 更靠近单个 PE 内部。

Function 仿真和 RTL 对比时会用到 Vector Dump。它的作用是把 CModel/ESL Model 的中间状态或接口数据导出，用来和 RTL simulation 的结果对齐。这样调试时不必只看最终输出，可以定位到模块接口、指令执行或数据搬运的具体差异。

Performance 仿真最后需要性能数据采集、处理和展示。文档这里是 Lark 同步块占位，PDF 导出后只留下“该内容不支持导出查看”，没有实际图像。能确定的是它的目标：采集性能相关事件和计数器，处理成可分析的数据，再通过统计表或 GUI 工具辅助定位瓶颈。

## ESL Modeling Methodology

`SiPU ESL Modeling Methodology` 这份文档的主线比较明确：先定义 CModel 是什么，再定义测试集是什么，最后说明它们在流片前和流片后的用法。它不是某个模型的实现说明，而是一套验证方法论，重点是让模型、测试集、RTL、Emulation、Chip 和软件栈在同一个项目周期里配合起来。

### CModel 是什么

CModel 是用软件实现的芯片行为模型。它有两个主要作用：一是在 RTL 或真实芯片可用之前，让架构验证、软件开发和性能评估先跑起来；二是在 RTL simulation、emulation 和 chip 调试时，提供可以对比的 golden reference。

PDF 里的标题层级有点乱，但实际语义上，CModel 下面可以拆成三类模型：

- Arch Model 主要模拟 SIPU 的编程接口和 ISA 计算执行。它不追求还原硬件模块内部细节，只要保证计算逻辑和精度与硬件一致。优点是开发快、好 debug，适合作为 Function Model 和 Performance Model 的参考。
- Function Model 关注硬件模块级行为和全系统功能仿真。它的目标是给硬件验证提供 golden reference，也给底层软件开发提供一个可运行的硬件模拟层。
- Performance Model 关注性能相关的硬件模块级行为。性能无关或影响很小的细节可以抽象掉，换取更快的仿真速度。

可以简单记成一句话：Arch Model 管语义和结果是否正确，Function Model 管模块行为和接口是否对得上，Performance Model 管性能趋势和关键指标是否符合预期。文档语境里，Function Model 和 Performance Model 合起来更接近前面说的 ESL Model。

### 测试集是什么

这里的测试集不是机器学习里的 dataset，而是一套可编译、可运行、能判断 pass/fail 的验证 workload。测试可以通过 Driver API、Runtime API 或上层框架编程下发，同一批测试可以跑在 Arch Model、Function Model、Performance Model、RTL Simulation、Emulation 和 Chip 上。测试集自身的正确性则通过 CPU/GPU reference 或 SelfCheck 交叉验证。

测试集大致分三层：

- Arch Tests，位于 `sipu_test` 这一类，覆盖 ISA tests、Arch Feature Tests、Programming Model Tests、HW Module Function Tests 和 module/system 级 Performance Tests。
- Library Tests，覆盖 GEMM 等算子库提供的计算和通信测试。
- Framework/Layer/Model Tests，来自 PyTorch、Triton 等框架，覆盖 layer、子图或完整 DL 模型级测试。

它的作用是把同一套软件场景贯穿整个芯片项目：早期验证架构和 CModel，中期验证 RTL 和 emulation，流片后做 chip bringup、量产筛片和软件调试。相比 UVM 随机激励，测试集更接近真实软件和真实 workload。

![ESL Modeling 项目时间进度](https://cdn.jsdelivr.net/gh/HatrixXXX/Hatrix-s-Blog-Image/img/methodology-project-timeline-clean.png)

这张图是在讲项目时间线。横向是项目进度，纵向是几条并行工作线：架构设计/验证、硬件设计验证、模型开发、测试集开发，以及 compiler、firmware、driver、library、framework 等软件开发。

图里的箭头表达的是依赖关系：模型开发为架构、指令和编程模型设计提供仿真平台，也为硬件验证提供 golden reference；测试集开发贯穿整个周期，既给模型提供功能/性能测试，也给硬件验证、emulation 和 chip bringup 提供真实场景激励；软件栈在没有真实芯片时依赖模型和 emulation 做开发调试，流片后再逐步迁移到真实 chip 上。

### 流片前怎么用

流片前主要分几件事。

第一是架构设计验证。架构团队用测试集和 CModel 验证架构选择、指令集实现、架构特性和编程模型。这个阶段更关心语义是否成立、功能是否完整、性能方向是否合理。

第二是硬件功能验证。测试集除了 RV/Tilecore 指令的基础测试，还会覆盖多 thread、多 TB、多 TBC、多 chip 的并行、同步和通信场景，也会覆盖 driver/runtime programming 这类异构编程特性。Function Model 在这些场景下提供 golden 输出，主要包括 Instruction Trace、Module Interface Transaction、NoC Traffic 和 Memory Traffic。

第三是硬件性能验证和软硬件联合调优。Arch Tests 里会包含模块级和系统级性能测试。有明确理论目标的测试，比如吞吐、带宽、cycle 数，Performance Model 和 RTL 都应该达到目标；没有明确理论目标的复杂 pattern，则要求 Performance Model 和 RTL 足够接近，并符合架构和微架构预期。Library/Layer 和 Framework/Model 级测试则更接近真实 workload，用来观察算子、layer 或完整模型的吞吐和 latency。

下面两张图都属于流片前硬件验证，分别描述 block/subsystem 粒度和 system 粒度的 RTL/CModel 对接。

![Function Model 与 RTL TestBench 对接](https://cdn.jsdelivr.net/gh/HatrixXXX/Hatrix-s-Blog-Image/img/methodology-function-rtl-testbench-clean.png)

这张图表达的是 block/subsystem level 的用法：Sequence 产生测试序列，Driver 把同一份激励送到 DUT、SV Model 和 ESL Model Module。Monitor 采集输出，Scoreboard 做对比。这里的 ESL Model Module 可以作为 golden reference，也可以输出 interface dump 给 RTL testbench 当激励。重点不是跑完整软件栈，而是验证某个模块或子系统的接口行为是否和模型一致。

![System Level 对接和 dump/IF 比对](https://cdn.jsdelivr.net/gh/HatrixXXX/Hatrix-s-Blog-Image/img/methodology-system-level-clean.png)

这张图表达的是 system level 的用法：Arch Tests、Library Tests 和 Framework Tests 都可以通过 Driver 下发，然后分别跑到 ESL Model、RTL Simulation、Emulation 或 Chip。ESL Model 和 RTL Simulation 之间通过 dump/IF 对齐，比较粒度可以落到 GCS、CNOC、DNOC、RV、Tilecore、memory transaction 等模块接口。它强调的是系统级交叉验证：同一批测试在不同后端上跑，发现差异后再按模块接口逐层定位。

RTL 和 CModel 对比不能简单做逐周期匹配。Polling loop、kernel launch 检测、kernel 间同步通信会让循环次数不固定；调度模块也可能因为时序不同而选择不同的 physical target module。NoC 和 memory 路径里，transaction 数量和顺序也可能不同。因此对比时常需要过滤、重排，或者带上 kernel、TBC、TB、thread 等 logical id 辅助匹配。

Emulation 阶段会逐步推进 Arch Tests、Library Tests 和 Framework Tests。它比软件模型更接近硬件，但调试时仍然可以拿 Arch Model 或 Function Model 的结果当参考，把 emulation dump 和模型 dump 做对比。

### 流片后怎么用

流片后，测试集和 CModel 继续有用，只是主战场从模型和 RTL 转到真实芯片。

Chip Bringup 会从 Arch Tests 开始，确认基本指令、编程模型和硬件模块行为，再逐步跑 Library Tests 和 DNN Layer/Model Tests。遇到问题时，可以把同一个测试放回 Arch Model 或 Function Model 里复现，用模型结果缩小差异范围。

量产筛片/Harvesting 阶段会从测试集中挑一部分作为 ATE 的补充。ATE 更偏结构化测试，测试集更接近真实 workload，速度也可能更适合批量筛选。设计得好的测试还可以帮助定位失效 module，为 harvesting 策略提供参考。

软件开发在流片后主要转到真实 chip 上进行，但 CModel 不会消失。它仍然适合做问题复现、离线 debug 和结果对照，尤其是在真实芯片上观察到异常、但需要更可控环境拆问题的时候。

## Vector Dump 和 DV 仿真环境

vector dump 是软件栈/Arch Model/CModel 跑过一个 case 后，把“如何初始化硬件、如何发 launch、期望结果是什么”落盘成 DV
testbench 可读取的文件包，简单来说就是“给 RTL/DV 复现实验用的一包输入激励 + 期望结果 + 元数据”。它的价值是把上层软件和 RTL 仿真解耦。DV 不需要重新跑 PyTorch/Triton/runtime/sikernel wrapper，也不需要每个 case 手写 testbench；只要读取统一格式的 vector，就能驱动 PE/PEC/PEG/chip 不同层级的 DUT，并把 RTL 输出和 dram_result 这类 golden result 对比。

DV 仿真环境就是用 vector dump 驱动真实 RTL DUT 的验证 testbench 环境，用来判断 RTL 是否和 Arch Model/CModel 的行为一致，并进一步分析性能瓶颈。

CModel/软件栈怎么和 RTL 仿真协同验证同一个 kernel/test case，核心是 Co-Sim 和 Vector-Sim 两种仿真方式。

## Arch Model 概述

Arch Model 主要用于验证 ISA 和软件侧的高层功能。它不是 RTL 级模型，重点是把 test、driver/runtime、command processor、计算集群、Spike 和 TileCore 串起来，让软件可以在接近硬件执行语义的环境里跑起来。

### 整体执行链路

![Arch Model 执行链路](https://cdn.jsdelivr.net/gh/HatrixXXX/Hatrix-s-Blog-Image/img/arch-model-flow.svg)

执行链路可以按下面的顺序理解：

1. Test 负责触发测试用例，包括按模块覆盖 tilecore 指令的 Asm tests，以及面向系统和 tilecore 的 High-level tests。
2. Sirt 扮演 driver/runtime 侧角色，负责分配资源、launch kernel、创建 dispatch packet，并把 packet 写入 ring buffer。
3. GCS-CP 负责处理 ring buffer 中的 packet。CPF 取 packet，CPE 解码 packet，CPD 把 Thread-Block-Cluster（TBC）任务派发给 CCS；任务完成后更新 ring buffer 读指针，并写 completion signal。
4. CCS 接收 CPD 下发的 TBC，把 TBC 拆成 TB；结合 PEC 中 RV、TileCore、L2B 等资源选择 PE；再把 TB 拆成 thread 发给 BD。TBC 完成后，CCS 向 CPD 回写 done signal。
5. BD 配置 tcsr，向 RV 发送 kernel start interrupt，并把 thread done signal 回给 CCS。
6. Spike 执行 RV thread，加载名为 `tilecore` 的 extension library。
7. TileCore 执行具体的 tile 指令。

### 主要功能模块

TileCore 通过向 Spike 注册 `tilecore` extension library 接入模型。Spike 调用 `tcore_decode` 取得 processor info、instruction 和 pc，TileCore 再根据 instruction 的 `tuop` 分发到对应模块。

| 模块           | 作用                                                               | 入口或实现                                                 |
| -------------- | ------------------------------------------------------------------ | ---------------------------------------------------------- |
| Tile Front-End | Arch Model 里没有独立 tile front-end，各 tilecore 模块自行解码指令 | 各模块内部解码                                             |
| Tile LSU       | TileCore 的 load/store 模块，支持 load、store 和 atomic            | `tcore_exec_mem`，实现位于 `tlsu.cc`                       |
| Tile MAC Unit  | TileCore 的矩阵计算模块                                            | `tcore_exec_mma`，实现位于 `tilecore_exec_mma.cc`          |
| Tile ALU       | TileCore 的向量级算术逻辑模块                                      | `tcore_exec_alu`，实现位于 `tilecore_exex_alu.cc`          |
| Tile Move      | 负责 tile register 和 RV register 之间的数据传输                   | `tcore_exec_mv`，实现位于 `tilecore_exex_mv.cc`            |
| Tile SFU       | TileCore 的向量级特殊函数模块                                      | 支持 sin、cos、sigmoid、tanh、rcp、sqrt、rsqrt、log2、exp2 |
| Tile DTE       | 负责大块数据拷贝                                                   | `tcore_exec_memacp`，实现位于 `tdte.cc`                    |
| Tile Sync      | 负责多线程同步                                                     | `tcore_exec_sync`，实现位于 `tilecore.cc`                  |
| Tile Config    | 负责 TCSR 寄存器读写                                               | `tcore_exec_cfg`，实现位于 `tilecore.cc`                   |

几个容易混淆的点：

- Tile LSU 会从 `memuop` 解码 `mem_fmt` 和 `mem_type`，再执行普通 load/store、block load/store 或 atomic。
- Tile MAC Unit 会从 38 个 `mmauops` 中解码 src/dst format，执行 M32、M16、M8、normal、A8W4、A6W6 等 micro operations。
- Tile ALU 支持 FP32、FP16、BF16，操作包括 conversion、transpose、add、mul、min、max、fma。
- Tile Move 支持 Tile to Vector、Vector to Tile、Tile to Scalar、Scalar to Tile、Immediate to Tile。
- Tile SFU 支持 FP32、FP16、BF16 数据格式。
- Tile DTE 会从 `acpuop` 解码并执行 linear copy、tiled copy 和 tiled-linear-conversion。
- Tile Config 支持 TCSR Read、TCSR Write、TCSR Write Immediate。

## SiPU ESL Model Framework

`SiPU ESL Model Framework` 这份文档更像框架使用说明，不是某个具体模型的架构设计文档。它关心的是一件事：怎么把硬件行为拆成可调度、可连接、可统计、可验证的软件模块。具体代码和配置字段很多，但对理解 ESL 建模来说，真正有用的是它划出的几条边界。

### 框架层级

![SiPU ESL Framework 层级](https://cdn.jsdelivr.net/gh/HatrixXXX/Hatrix-s-Blog-Image/img/framework-hierarchy-clean.svg)

框架的顶层是 engine，下面按 clock region 划分时钟域，再往下才是 block。block 是真正承载硬件行为的建模单元。这个层级大致对应：

- engine 负责搭模型、连跨时钟域通路、判断仿真是否结束。
- clock region 负责表达一组共享时钟节奏的模块。
- block 负责每个周期要发生的行为，以及 block 内部子模块和接口的组织。

文档里反复出现 scheduler，是因为这个框架不是简单单线程顺序跑所有模块。block 之间、clock region 之间，甚至 engine 之间，都预留了并行仿真调度能力。也就是说，模型结构本身要服务两个目标：一是像硬件一样分层，二是让仿真器知道哪些部分可以被调度。

### 配置在这里的角色

配置文件不是重点，重点是它把模型里容易变化的东西外置了。比如输出开关、统计开关、线程调度策略、时钟频率、FIFO 深度、pipeline 延迟、pipe 数量等，都不应该散落在模型代码里。

这样做的价值很直接：同一个模型可以用不同配置跑功能验证、性能采样、vector dump 或多线程仿真。对架构探索来说，这比反复改代码可靠得多。

### block 开发的主线

一个 block 的生命周期可以简单理解为三步：

1. 先搭内部结构。
2. 再把输入输出和子 block 接起来。
3. 仿真时每个周期执行一次行为更新。

文档给的例子把一个 block 拆成多个 stage，并且在时钟函数里从后级往前级处理。这一点很关键。流水线建模不能只看“数据往前走”，还要先让下游释放空间，再决定上游能不能推进。否则 backpressure 和 latency 很容易被模拟错。

![SiPU ESL Framework 流水线示例](https://cdn.jsdelivr.net/gh/HatrixXXX/Hatrix-s-Blog-Image/img/framework-pipeline-example-clean.svg)

这张图可以按数据流来看：source 进入 block1，block1 内部有多级 stage，中间夹着 FIFO 和 pipeline；输出跨到另一个 clock region 的 block3，再送到 sink。它说明 ESL block 不是随便写一个函数，而是在软件里重建硬件的队列、打拍、延迟、反压和跨时钟域连接。

### port 是模块间通信边界

文档里最值得记住的约束是：仿真进入 simulation 阶段后，block 之间传信息必须走 port，不能直接通过指针修改别的 block 的内部状态。

这个约束不是形式主义。只要框架允许并行调度，共享可变状态就会让模型结果依赖调度顺序，最后很难判断 bug 来自硬件语义还是软件模型本身。port 把通信边界固定下来，也让接口数据 dump、性能统计和调试更容易做。

通过 port 传递的数据对象类似共享指针语义，上下游不能同时读写同一份 packet 内容。这里的意思是：数据可以共享所有权，但行为上仍然要像硬件 transaction 一样有清楚的生产者和消费者。

### FIFO 和 pipeline 是硬件语义，不只是容器

框架内置了 FIFO、普通 pipeline 和 latency pipeline。表面看它们像 C++ 容器，实际上它们承担的是硬件时序语义：

- FIFO 表达缓存、队列深度、满空状态和吞吐压力。
- pipeline 表达多级打拍，以及前后级之间的推进关系。
- latency pipeline 更强调固定延迟或近似固定延迟的数据返回路径。

这些结构还内置性能数据采集。也就是说，建模时不只是为了让功能结果对，还要在同一套结构上观察占用率、等待、阻塞和吞吐。ESL Model 的价值就在这里：它比 Arch Model 更接近硬件模块和时序，又比 RTL 更快、更容易插统计点。

### 跨时钟域和跨 engine 连接

同一时钟域内的连接通常在父 block 里完成，跨时钟域的连接由 engine 统一处理。这个分工可以避免 block 自己知道太多全局结构。

从建模习惯上看，这是一条比较重要的边界：局部模块只描述局部拓扑，系统级连接由更高层管理。这样模型变大以后，block 不会因为跨层引用越来越多而变成一团难维护的全局对象。

### 性能和调试钩子

框架提供了几类观测手段：

- hierarchy log：记录模型层级，方便确认搭出来的结构是不是预期的结构。
- counter：记录周期数、事件次数、队列命中次数之类的计数指标。
- duration event：记录某个事务或阶段持续了多久。
- instant event：记录某个瞬时事件，适合看关键状态变化。
- log：按 verbosity 控制普通调试输出。
- vector dump：导出 block/module 接口数据，用于 block、subsystem 或 system level verification。

这些东西放在一起，说明这个 framework 的目标不是“能跑起来”就结束，而是要支持定位问题：功能错了能看接口数据，性能差了能看计数器和事件，结构不对能看 hierarchy。

### 和外部模块的关系

文档只列了 cycle based 和 event based 两类外部代码模块集成方式，没有展开细节。可以先按概念理解：

- cycle based 更像每个周期都被 ESL 调度器推进一次，适合和硬件周期行为对齐。
- event based 更像由事件触发状态变化，适合处理稀疏事件、外部模型或不需要逐周期推进的模块。

具体怎么接还得看框架代码或测试用例，PDF 里没有给出足够信息。

### 我会怎么记这份文档

这份文档的精髓不是那些声明宏和接口参数，而是它对 ESL 模型提出了四个要求：

1. 结构上要分清 engine、clock region 和 block。
2. 通信上要通过 port，不能靠共享可变对象偷懒。
3. 时序上要用 FIFO/pipeline/latency pipeline 表达延迟、反压和吞吐。
4. 验证上要同时留下 hierarchy、counter、event、log 和 vector dump。

如果只把它当 C++ API 手册看，会觉得内容很碎；如果把它放回芯片验证链路里看，它其实是在回答一个问题：怎么写一个既能代表硬件行为，又能被软件栈、性能工具和 RTL/DV 验证流程使用的 ESL 模型。

### SIPU 硬件总体架构

SIPU 的总体结构可以按三层记：PEG、PEC 和 PE。整体分成两个 PEG（Group），每个 PEG 包含四个 PEC（Cluster），每个 PEC 包含四个 PE，所以一共有 32 个 PE。

![SIPU 硬件总体架构重绘图](https://cdn.jsdelivr.net/gh/HatrixXXX/Hatrix-s-Blog-Image/img/sipu-top-architecture-clean.svg)

每个 PE 配备 1MB 的 L2B，作为 shared memory；每个 PEC 配备 4GB DRAM，四个 PEC 的 DRAM 以 interleave 方式组成一个 16GB 的整体，作为 global memory。

![SIPU PEC 和内存组织重绘图](https://cdn.jsdelivr.net/gh/HatrixXXX/Hatrix-s-Blog-Image/img/sipu-pec-memory-clean.svg)

L2B 是 L2 Buffer，由 SRAM 做成，挂在 PE 旁边作为本地存储区。它的作用是降低全局带宽需求、降低访问延迟，也减少功耗。L2B 更接近显式管理的数据缓冲区，可能由 DMA、编译器或调度器控制，不像 CPU cache 那样完全由硬件自动管理。加速器的数据访问模式通常更规则，很多访问可以提前知道，所以显式 buffer 往往比自动 cache 更可控。

L2C 是 L2 Cache，属于硬件自动管理的缓存机制。程序员按地址访问，不需要直接控制 cache 的交互。cache line 是 cache 读写、命中和替换的基本单位；不同硬件单元同时访问同一个 cache line 时，可能触发额外同步、失效、刷新和重载，性能会下降。

L2B 和 L2C 都在存储层级的第二级，所以都叫 L2。按离计算单元从近到远，可以粗略分成寄存器、L1、L2、L3 或 Global Buffer、DRAM/HBM。

interleave 是交错编址：把多个 DRAM 组合成一个更大的逻辑内存空间。这里的 interleave 粒度是 4KB，意思是每 4KB 轮流放到不同 DRAM 里。它的目的不是单纯扩大容量，而是提高带宽，避免单个 DRAM 变成瓶颈，并让访问更均匀地打到多个 DRAM 上。

单个算子可调度的范围是一个 PEG。SIPU kernel 里几个维度的可配置范围大致是：`grid` 为 1 到 4096，`cluster` 为 1 到 4，`block` 为 1 到 2。

### PE 内部结构和执行粒度

每个 PE 包含两个 RV Core 和一个 Tile Core，共享 L2B；L2C 的 cache line 是 64Byte。寄存器资源可以这样记：

- RV Core scalar 整型寄存器：32 个，单个 64 bit。
- RV Core scalar 浮点寄存器：32 个，单个 64 bit。
- RV Core Vector 寄存器：32 个 vec，单个 1024 bit。
- Tile Core Vector 寄存器：256 个 TReg，单个 1024 Byte。

![SIPU PE 内部结构重绘图](https://cdn.jsdelivr.net/gh/HatrixXXX/Hatrix-s-Blog-Image/img/sipu-pe-microarchitecture-clean.svg)

PE 内还包含 TLSU、TALU、DTE 等硬件单元。程序以线程为单位执行，多个线程共享一个 PE 时，需要配置这些寄存器如何分配给不同线程。

`grid`、`cluster`、`block` 和硬件层级之间不要机械等同。这里可以这样理解：

- `grid` 是逻辑概念，不直接对应某个硬件数量。`gridDim` 表示总共有多少个 block 要执行，相当于任务总数，最多可以设到 4096。
- `cluster` 对应到 PEC 这个层级，`clusterDim` 表示 cluster 内启用的 block 数量，可设 1 到 4。
- `block` 对应到 PE 这个层级，`blockDim` 表示 block 内 thread 数量。由于一个 PE 里有两个 RV Core，这里可设 1 到 2。

### 程序开发工具 `siorigin_tile`

算子开发依赖两类基础能力：runtime 提供的基础功能 API，以及 compiler 提供的 Tile Core 和 RV Core API。当前 kernel 开发主要使用 Tile Core builtin 指令集合和 RV Core builtin 指令集合。

runtime 封装的编译工具是 `scc`，用法和 `gcc` 类似。直接调用编译器可以工作，但更推荐用 CMake 集成管理：

```cmake
cmake_minimum_required(VERSION 3.27)
project(MySipuApp)

find_package(scc REQUIRED)

scc_add_executable(v vectMul.su v1.su)
scc_target_include_directories(v ./include1 ./include2)
scc_target_compile_definitions(v ENABLE_DEVICE_KERNEL_LAUNCH=1)
scc_target_compile_options(v "-O0" "-Wall")
scc_install(v DESTINATION bin)

scc_add_library(v2 SHARED v2.cpp)
scc_target_compile_options(v2 "-O2")
scc_install(v2 DESTINATION lib)
```

编译器标识符和 CUDA 类似，也有 `__global__`、`__device__`、`__shared__`。`disable_tile_scheduling` 可以作用在 `global` 或 `device` 函数上，编译器会尽量让这些函数里的 Tile 指令按源代码顺序出现在汇编中，这通常叫 Tile 指令保序。

为了提高执行效率，有时还会手写汇编，也就是直接编排 Tile Core 和 RV Core 的指令。手写汇编的目的通常有两个：一是调整指令顺序，让不同功能单元持续有活干；二是展开寄存器使用，减少数据依赖。

`builtin` 指令是编译器内建指令，属于源代码层面的特殊接口。汇编指令则是 ISA 层面的具体指令。`builtin` 的价值在于：让源代码能表达普通 C/C++ 语法无法表达、但硬件确实支持的能力。

SIPU 编程模型是典型的 host-device 异构模型，包含主机端代码和设备端代码。算子的核函数可以通过 `grid`、`cluster`、`block` 指派多个线程。一个数组相加例子如下：

```cpp
#include <sipu_runtime.h>

__global__ void add(const int* A, const int* B, int* C, int n) {
    uint32_t id = blockDim.x * blockIdx.x + threadIdx.x;
    uint32_t step = blockDim.x * gridDim.x;

    for (uint32_t i = id; i < n; i += step) {
        C[i] = A[i] + B[i];
    }
}

#define N 1024

int main(int argc, char* argv[]) {
    size_t dsize = N * sizeof(int);
    int host_A[N];
    int host_B[N];
    int host_C[N];

    int* data_a = nullptr;
    int* data_b = nullptr;
    int* data_c = nullptr;
    sipuMalloc(&data_a, dsize);
    sipuMalloc(&data_b, dsize);
    sipuMalloc(&data_c, dsize);

    sipuMemcpy(data_a, host_A, dsize, sipuMemcpyHostToDevice);
    sipuMemcpy(data_b, host_B, dsize, sipuMemcpyHostToDevice);

    dim3 grid{16};
    dim3 block{2};
    add<<<grid, block>>>(data_a, data_b, data_c, N);

    sipuMemcpy(host_C, data_c, dsize, sipuMemcpyDeviceToHost);

    sipuFree(data_a);
    sipuFree(data_b);
    sipuFree(data_c);

    return 0;
}
```

### 开发特性和底层优化注意点

如果循环里同时有访存和计算，要尽量减少两者之间的相关依赖。相关依赖可以分成真依赖和假依赖。真依赖是实际的数据依赖，例如 `reduce(v1, v2)` 必须等待 `v1 = tmv(...)` 完成，因为计算确实需要 `v1` 的结果，这类依赖不能消除。假依赖通常来自寄存器名复用，例如多次迭代都复用 `v1`。把 `v1` 展开成 `vvec[0]` 到 `vvec[7]` 这类不同寄存器，可以消除假依赖，让访存单元在当前数据计算时提前加载下一批数据。

为了避免 cache line 冲突，Tile Core 不要主动访问 kernel 代码里的栈空间。换句话说，不要把局部变量地址直接传给 Tile Load/Store。

RAS（Return Address Stack）是 RV Core 的函数调用返回地址预测硬件，只有 4 级深度。函数调用层次太深时，返回地址预测会失效，流水线会被打断。性能敏感代码里，调用层次不要太深；少量短函数建议直接标 `inline`。

RV Core 的分支预测器能力有限，没有间接跳转预测器，主要依赖直接跳转预测器（JAL，jump and link）。`switch-case` 编译出来的间接跳转预测效果比较差，应该少用。`if/else` 也尽量用于判断 thread id 之类结果稳定的条件，这样分支预测器更容易学到固定模式。

在 AI 加速器的类型系统里，`m1`、`m2`、`m4`、`m8` 表示一个对象占用了多少倍基础向量或 tile 资源，也就是寄存器宽度倍数。`union` 是 C/C++ 里的联合体，所有成员共用同一块内存，同一时刻本质上只有一种解释方式。这里可以用它处理一种尴尬情况：数据访存支持 `m2` 级别操作，但运算操作不支持。

推测执行的本质是：控制流还没最终确定前，先把大概率会执行的指令拿进流水线执行。普通计算指令通常可以推测执行，因为即使猜错，副作用也较小；访问特殊硬件状态、发起复杂访存、或者有不可轻易撤销副作用的指令通常不适合推测执行。Tile Core 指令、RVV 指令和 CSR 操作都更接近后一类。

因此在循环体和函数内，标量指令尽量密集放在靠前位置，位置无关的指令也尽量提前。每个循环最好做大一点，用循环展开平摊分支预测带来的 bubble。不要把 Tile 指令写在太小的循环里，否则一次跳转对应的运算太少，很难填满 Tile 指令的长延迟。

`tadd` 产生的寄存器依赖大约需要 14 个 cycle。也就是说，`tadd` 的结果写回 Tile 寄存器后，后续依赖这个结果的指令至少要隔开 14 个 cycle，或者插入足够多的无关指令来填充这段延迟。

如果只是把一个 Tile 寄存器的数据拷贝到另一个 Tile 寄存器，优先考虑用 `tadd + 0`，而不是 `tmv`。`tmv` 走 ACE 流水线，发射效率只有 1 inst/cycle；`tadd` 走 TALU 流水线，吞吐更高，也不容易让 ACE 成为瓶颈。

算子 kernel 代码还要注意 load、store、mma 指令的配比。某一类指令太密集，可能导致对应流水线发不下去。load/store 建议优先使用 M1，因为硬件对 M1 的解依赖最快。这里的解依赖指硬件用 scoreboard 或 hazard detector 判断依赖数据是否准备好，准备好就发射下一条指令，否则等待。

### 数据格式、IDE 补全和内存管理

地址对齐可以理解为硬件希望数据从固定大小的边界开始存放，而不是从任意地址开始。首地址对齐指数据块第一个字节的地址满足对齐要求。比如要求 32B 对齐，就表示首地址必须是 32 的整数倍。硬件访问数据通常一次读一整块；不对齐时，一次访问可能跨块，最后变成两次访问。Linear 搬运一次搬一个 RV Vector，要求 32B 对齐；Tiled 搬运一次搬整个 Tile 的一部分，要求 256B 对齐。

BF16 和 FP16 都是 16 位浮点数，但位分配不同。FP16 是 1-5-10，即 1 bit 符号位、5 bit 指数位、10 bit 尾数位，精度较高但范围较小。BF16 是 1-8-7，指数范围和 FP32 一样，尾数更短。神经网络通常不需要很长的尾数，但需要较大的指数范围，所以 BF16 被 TPU、CPU、GPU 和各类 AI 芯片广泛支持。TF32 是 NVIDIA 在 Ampere 架构里提出的 AI 计算格式，在 FP32 的基础上缩短尾数，让有效 bit 参与运算，从而提高吞吐。

IDE 自动补全 Tile Core 指令，并不是因为 clangd 天然认识这些指令。更准确地说，这些指令在 SIPU SDK 头文件里被声明成 builtin 或 intrinsic 函数，clangd 能读取这些声明。clangd 可以理解为 Clang 编译器前端的代码分析服务。Clang 属于 LLVM 项目，LLVM 还包含 LLVM IR、优化器和 x86/ARM/RISC-V 等后端。`gcc/g++` 和 `clang/clang++` 都能编译 C++，前者属于 GNU 项目，后者属于 LLVM 项目。LLVM 的错误提示、IDE 支持和可定制性更好，所以不少 AI 芯片厂商会基于 LLVM/Clang 做二次开发。

栈、堆、全局区（data/bss）本质上都是地址空间中的一段区域，最后都会映射到真实内存里，区别主要是管理方式。局部变量通常在栈上，函数返回后自动回收；`malloc/new` 申请的对象在堆上，需要手动或由运行时管理释放；全局变量和静态变量通常在 data/bss。之所以会产生栈访问，常见原因是局部变量无法全部放进寄存器，发生寄存器溢出后，编译器会生成保存到栈上再取回的指令。

### Cooperative Launch、DTE 和流水线同步

SIPU 支持 Cooperative Launch，类似 CUDA Distributed Shared Memory。它允许同一个 cluster 内的 PE 互访 shared memory。本 PE 内的 shared memory 可以直接访问；访问其他 PE 的 shared memory 时，需要通过地址 map API 转换后再访问。

DTE 可以用于多种数据搬运场景，用来提高搬运和计算的并行效率。Linear 数据搬运只需要指定源位置、目标位置和数据大小，例如从 global memory 搬到 shared memory。Tile 数据搬运面向 Tile Format 数据，需要结合 tensor map 结构和坐标信息。DTE 还支持 Linear 和 Tile 两种排布方式之间的转换。

SIPU 内存在多种相互独立的指令流水线。比如 RV Core/TLSU、load/store、TALU、TMAC、TSFU 和 TDTE 都可能有自己的 pipeline。不同类型的指令会进入不同流水线，流水线之间本身可以独立推进；但数据不是独立的，所以需要同步，保证一个流水线要使用的数据已经被另一个流水线准备好。

同步可以分成几个层次：线程内同步、单线程内不同指令流水线之间的同步、多线程同步，以及访存相关同步。对多个 pipeline 的访存控制，也需要配套的访存同步指令。

### 性能分析方法

算子开发完成后，如果通过测试用例验证了其功能的正确性，那么对其性能进行分析与优化，则是提升系统整体运行效率的关键步骤。

在芯片未回片的情况下，通常会使用各种仿真工具进行功能验证与性能分析，包括perf model，QEMU，RTL仿真验证等。ESL Model的介绍上面已经说了。RTL仿真是在真实的硬件环境中进行算子的实测，并输出跑测结果。在ETX设备上，当RTL仿真执行完成后，会在对应目录下生成一系列文件，可通过浏览器以本地文件浏览方式，直接打开该目录内的html文件，即可查看指令执行情况与统计信息。PMU (Performance Monitoring Unit) 是 SIPU 芯片内置的硬件性能计数器模块。每个硬件模块（PE、DRAMIF、C2C 等）都有一组计数器，可以在程序运行期间记录各种事件的发生次数或周期数。PMU 计数器只做累加操作，硬件上没有为中间状态值预留存储空间，因此不支持分时采样（time-sharing sampling）。这意味着每次采集只能获得从 reset 到 stop 之间的累计总数，无法获取过程中的时间序列数据。

除了以上对kernel内部指令执行逻辑与性能的分析，通常需要统计分析算子总的执行耗时情况，有多种方法可以实现。可以使用C++提供的标准库中的接口，来衡量kernel执行的端到端时间。此种方法的粒度最为粗糙，但是与实际使用中的情形最为接近。EVENT接口是SIPU runtime提供的轻量化时间统计接口，用于精确指定要测量的代码段，不需要额外链接库。EVENT接口的使用，不限于单个kernel，可测量多个kernel、memcpy的组合耗时。

RTL仿真和EMU仿真的波形抓取和查看、PMU工具的使用和分析：在SIPU Programming Guide，以及收藏夹的几篇文档中有介绍。单个 sikernel case 生成 arch_model vector dump有专门的文档。
